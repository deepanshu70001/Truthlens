## Pipeline and status-model audit

Source reviewed at E0: `backend/app/services/orchestrator.py`, `backend/app/services/reporting/builder.py`, `backend/app/services/evidence/schema.py`, `backend/app/services/fusion/engine.py`, and the API endpoints. The observations below preserve the E0 baseline; see the E1 amendment after them for current behavior.

- `StageResult` documents `pending | running | completed | failed | skipped`; runtime code also assigns `partial` and `unavailable`. The stage runner preserves only `partial`, `failed`, `unavailable`, and `skipped` from service results. Service-level `success` and `no_results` are normalized to stage `completed` when the service is called; no-eligible-claim fact-check is a separate branch that explicitly records the stage as `skipped` and adds a `no_results` result to report data.
- The `no_results` fact-check behavior reflects that no eligible claim was available to query, not a successful search with an empty provider response. The report should distinguish this from provider `no_results`.
- Most stages are optional. Their failures do not abort the remaining pipeline. `build_report` can represent partial status when stage outcomes include failed/unavailable/partial, while skipped alone does not make the report partial. The ORM analysis status is set to completed after pipeline assembly; status API then maps it to `partial` when stored report status is partial. Consequently ORM status and report status can differ.
- `_run_stage` writes stage metadata including `{available: true, type: <class>}` and an `output_reference` such as `report.<stage>`; full result values are written into the report itself, not retained in `StageResult.result`. This is a reference rather than a persisted stage-output payload.
- `completed_steps` is computed only from stages whose status is exactly `completed`; partial/unavailable/skipped/failed stages are omitted even after they finish. The total is hard-coded as 20. Skipped-stage recording does not advance `current_step`. Progress can therefore undercount completed work or remain misleading on optional/conditional paths.
- The outer pipeline exception handler attempts to persist a failed report/state. It can log and swallow persistence failure if the database is unavailable; therefore a final state is not guaranteed under DB failure. Early missing-analysis returns and missing asset/path failure handling also have distinct persistence behavior that should be normalized.
- Outputs are assembled into the report and passed through evidence/fusion; fusion conservatively avoids directional authenticity votes when calibration is absent and treats forensic cues as informational. This does not make the combined assessment calibrated.
- Orchestrator call sites include metadata, quality, authenticity, forensics, OCR, vision, conditional XAI, text normalization, claims, fact-check, provenance, hashing, evidence, fusion, explanation, virality, regional spread, social impact, and report assembly. Preprocessing is run on upload and its record is carried into analysis. VLM, dedicated language detector, translation, C2PA parser, and content-spread trajectories are not active orchestrator stages.

### E1 requirements captured by this audit (baseline, before E1)

1. Define one shared stage/service status vocabulary and preserve the distinction between `no_results`, `success`, `skipped`, `unavailable`, `partial`, and `failed`.
2. Record skip reasons and advance progress for every terminal stage; derive total/current/completed progress from the actual pipeline plan.
3. Align persisted `Analysis.status`, report status, and API status; ensure optional failures are visibly represented without claiming full success.
4. Make report output retention and stage references explicit and stable; avoid treating a type-only result as the stage output.
5. Guarantee a recoverable terminal state when a task fails, including persistence-failure strategy and restart recovery. Durable worker implementation remains in Stage 4.
6. Add focused tests for status mapping, no-eligible-claim versus provider-empty results, optional failure, exception persistence, and conditional progress.

## E1 amendment — current status

`backend/app/services/stage_contract.py` now normalizes execution status separately from service outcome. `StageResult` carries canonical status, outcome, safe error message, stable IDs, timestamps/runtime, warnings/limitations, module identity, and a report output reference. `completed_steps` reads old list records and now persists successful steps plus a complete stage-status map; terminal progress includes failed, unavailable, partial, and skipped states. Optional degraded stages produce a partial report and status API response. Terminal pipeline exceptions roll back and attempt a failed-report persistence with one bounded minimal-report retry. Fact-check/provenance failure evidence carries its failed/unavailable status and is ignored by fusion.

The DB enum remains `queued | processing | completed | failed`; report/API compatibility derives `partial` from the report rather than introducing a DB enum migration. The production detector/calibration/identity/voting policy is unchanged. E1 tests and validation results are recorded in `docs/e1_failure_handling_report.md`. Durable worker recovery and frontend browser E2E remain outstanding for later stages.
