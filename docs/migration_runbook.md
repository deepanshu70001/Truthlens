# TruthLens database migration runbook

## Supported migration chain

- `20261122_01` — baseline/adoption of the pre-E8 schema.
- `20261122_02` — durable jobs, ownership, queue/worker lease, shared rate-limit storage and indexes.

Use the same `DATABASE_URL` as the API and worker. The migration environment reads the `DATABASE_URL` environment variable first, then project settings. The repository's default is local SQLite; production configuration requires PostgreSQL with the async `asyncpg` driver.

## Fresh database

1. Provision the database and configure `DATABASE_URL`.
2. From repository root, run:

   ```powershell
   python -m alembic upgrade head
   ```

3. Verify the revision:

   ```powershell
   python -m alembic current
   python -m alembic check
   ```

4. Start the API and separate analysis worker only after the migration succeeds.

## Existing pre-Alembic database

1. Stop API/worker writers and take a verified backup of the DB and `STORAGE_PATH` together.
2. Point `DATABASE_URL` to the existing DB and run `python -m alembic upgrade head`.
3. The baseline validates the legacy core table columns and adopts those tables without recreating them. The next revision adds nullable ownership and new durable tables, then backfills queued/processing analyses to queued jobs. It retains report/image rows and JSON and resets only interrupted stage state.
4. Verify `alembic_version` is `20261122_02`, inspect migration logs, confirm counts of legacy analyses and reports against the backup, then start API/worker.

Do not run `Base.metadata.create_all` manually to bypass a migration error. Production startup checks the current migration head and refuses missing/outdated schema.

## Rollback

The baseline downgrade does not drop the original four tables. Revision `20261122_02` refuses downgrade while job history, owner values or outstanding jobs would be lost. The downgrade is intentionally not a data-erasure tool. If deployment rollback is required, restore the coordinated DB/storage backup or ship a forward migration after review. Do not delete migration rows/tables by hand.

## Data preservation and cleanup

Migration tests use isolated temporary SQLite files. They verify fresh upgrade, existing legacy upgrade, report sentinel preservation, queued job backfill, counter seed, schema drift check and destructive-downgrade refusal. They do not inspect or migrate the ignored local `truthlens.db`.

Analysis deletion is an explicit user action and removes its own generated storage paths after DB commit. The orphan scanner is report-only. Staging cleanup removes only aged `.uploading` files generated by the application. There is no automated analysis retention/deletion. Never point storage cleanup at `datasets`, `research_evidence`, `experiments`, model/checkpoint folders or protected evaluation directories.
